F S09-F5 [L182 MISSING medium] The plan does not say which counter value is stored or how the certificate is tied to the request. Two standard attacks on time protocols work even when messages are authenticated: holding a message back (delay manipulation) and replaying an older valid message. Suppose the phone stores the counter when the response arrives and accepts any valid certificate. A student who controls the network path can then hold the response, or inject a certificate captured earlier, and shift the computed time back by that gap. On iPhone this only needs a user-installed root certificate with full trust, which Apple allows. Android apps targeting API 24+ ignore user CAs by default, so there it needs root. Roughtime handles both with a client nonce and a maximum request-to-response delay. F S09-F6 [L973 SIMPLIFY low] No time-stamping standard fits better than a small MAC'd token. Roughtime (draft-19, March 2026, Experimental, in the RFC Editor queue) is built for clients that do not trust a single server: it queries at least three servers over UDP/TCP and uses Ed25519 delegation. RFC 3161 needs a Time Stamping Authority and CMS SignedData. Here only our own server issues and checks the certificate. An HMAC over (server time, device id, client nonce) using Node's built-in crypto is the smallest option, and the phone never needs to verify it. Returning a fresh certificate on every server response (send, sync, version check) keeps anchors fresh without extra requests at the class-exit peak; this is the piggyback approach Elson and Römer describe. It also replaces the separate refresh on network change in line 192. | URL https://datatracker.ietf.org/doc/html/draft-ietf-ntp-roughtime-19
