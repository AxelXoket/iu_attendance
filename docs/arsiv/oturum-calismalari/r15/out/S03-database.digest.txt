F S03-F04 [L612 BETTER medium] A client-chosen UUID used as the idempotency key needs guards the plan does not state. (1) Fingerprint: if the same id arrives with different signed bytes or from another device, answering 'zaten var' silently drops a real record; the IETF Idempotency-Key draft says to reject a reused key with a different payload and to look up on a composite of the key and client attributes. (2) Validate the key format: CHECK (uuid_extract_version(id) = 7) is cheap. (3) Never use the timestamp inside the id: it comes from the phone clock, which the plan distrusts, and PostgreSQL notes the extracted timestamp is not necessarily the generation time. (4) With three unique rules on one table (id, device+seq, session+student), a 200-record batch using ON CONFLICT on one target still raises on the other indexes and aborts the whole transaction; ON CONFLICT DO NOTHING without a target handles all unique indexes, after which each record is classified. Minor wording: UUIDv7 is 16 bytes like v4; its gain is index locality, not small indexes, and ids arriving up to 7 days late keep that gain only in part. | URL https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html
  REC: Telefonun ürettiği kimlik tekrar gönderme anahtarı olarak kalır, şu kurallarla: Aynı kimlik farklı imzalı baytla ya da başka cihazdan gelirse 'zaten var' değil 'ret' döner ve kayıt işaretlenir.
